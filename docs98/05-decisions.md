## D-003 — Drop Electron by building a custom host, not by rewriting the UI natively (2026-10-11) — proposed
- **Decision:** Provide a minimal DOM/CSS/render layer + JS engine + Node shim so the existing workbench runs largely unchanged.
- **Why:** The workbench is ~1.1M lines written directly against the DOM; a native rewrite would lose most features. Goal is the full feature set.
- **Alternatives rejected:** (1) native toolkit rewrite — too large, loses extension compatibility; (2) WebView2/Tauri — requires newer Windows, defeats the goal; (3) plain Electron backport — can't reach XP/98.
- **Risk:** Performance of a small JS engine and a custom renderer; breadth of CSS needed. Phase 1 spikes test this.
- **Evidence (spike 8, 2026-10-12):** the unmodified web workbench boots on our DOM/CSS/layout/renderer on QuickJS-ng and responds to input (Welcome page, views, chat, dialogs, quick input, typing in Monaco). Cost: 131 full restyle passes per boot (165 of 175 s), ~10 s per keystroke, 666 to 683 MB peak RSS: all addressable in the engine (incremental invalidation, memory), none in VS Code. Desktop workbench (needs a main-process shim), extensions and Windows are untested. [spikes/08-workbench-boot/README.md](spikes/08-workbench-boot/README.md).
- **Evidence (spike 10, 2026-10-12), for D-006 (process/IPC model):** the Electron-free process model needs no change to VS Code: run its own electron-main on the host JS engine with a ~190-line `electron` stand-in, utility processes as child processes with `process.parentPort`, ports relayed by main (to be replaced by a direct design), JSON/binary-framed IPC to the window. The desktop workbench, shared process, file service, extension host and git extension work end to end on QuickJS-ng (Linux). [spikes/10-main-shim/README.md](spikes/10-main-shim/README.md).
- **Evidence (spike 9, 2026-10-12):** the biggest cost found in spike 8 is gone: incremental style invalidation (planner over a mutation log, rule-set analysis with key/shape sets, rule-set delta, verified against a full restyle) takes the workbench boot from 175 s to 32 s and a keystroke from ~10 s to ~0.1 s on the same machine, with identical computed styles on a complete boot and over 650,000 fuzzed passes. What is left is price per restyle (2 to 4 ms on QuickJS), rule-index rebuilds on stylesheet changes (0.5 to 2.3 s), memory (607 MB peak) and layout cost per pass. [spikes/09-incremental-style/README.md](spikes/09-incremental-style/README.md).

## D-004 — JS engine — proposed (pending Phase 1)
- **Candidate:** QuickJS / QuickJS-ng. Others to compare: older V8 builds, Duktape, other embeddable engines.
- **Criteria:** buildable for Win 7/XP/98, ES level support, speed, memory, multi-context/worker support.
- **Evidence so far (spike 1, step 1, 2026-10-12):** QuickJS-ng 0.17.0 compiles all 30 bundle files unmodified (language level OK); workbench compile 2.8 to 3.4 s but 0.2 s from precompiled bytecode (so ship bytecode); 86 MB compiled heap for the workbench; lacks `Intl`, `WebAssembly`, `structuredClone` (must be supplied); its Windows sync layer uses Vista+ APIs (fine on Win 7, to be replaced for XP/98). **Spike 2 (execution speed, 2026-10-12):** on the TypeScript compiler QuickJS-ng gives identical results, is 8.5× slower than V8 with JIT (2.3× to 15× by phase) and 2.2× slower than V8's JIT-less interpreter, memory +15%; the Node-side bundles boot on it with a small shim ([spikes/02-node-shim/README.md](spikes/02-node-shim/README.md)). **Spike 3 (2026-10-12):** real extension code loads: 24 of 34 built-in extensions activate on QuickJS-ng through a ~120-line JS CommonJS loader; QuickJS cannot `require()` ES modules synchronously or take a module-resolver hook from JS, so a native module loader is needed for ESM-only dependencies (pre-bundled to CJS for now) and ES-module extensions ([spikes/03-extension-loading/README.md](spikes/03-extension-loading/README.md)). **Spike 4 (WebAssembly, 2026-10-12):** QuickJS-ng has no `WebAssembly`; `vscode-oniguruma` still runs on it three ways with identical results (wasm3 with a custom JS API, native libonig, wasm2c-translated C). Native and wasm2c match V8 per call, wasm3 does not (8× slower per call, 2.6× to 4.9× slower tokenization) so the engine needs a native Oniguruma (or wasm2c) module, not a general WASM interpreter; tree-sitter is experimental/default-off and unproven on wasm3 ([spikes/04-webassembly/README.md](spikes/04-webassembly/README.md)). ES5-only engines are excluded (esbuild cannot lower below ES2015). Details: [spikes/01-js-engine/README.md](spikes/01-js-engine/README.md). **Spike 5 (child processes, 2026-10-12):** on the same engine a forked tsserver gives identical answers to Node and runs 6.0× slower (1.12 s vs 6.73 s on a 19-file project; x86-32 8.3 s); an idle QuickJS child needs 4 MB RSS vs Node's 39 MB and the tsserver child peaked at 200 MB (125 MB as x86-32) vs 265 MB. Native UTF-8 conversion is required (a JS `TextDecoder` made IPC 60× slower); the engine's module-loader hooks are enough for Node's ESM resolution and synchronous `require(esm)` ([spikes/05-child-process/README.md](spikes/05-child-process/README.md)). Still `proposed`.

## D-005 — Render strategy — proposed (pending Phase 1)
- **Candidate:** Minimal DOM + CSS layout engine drawing via GDI.
- **Open:** how much CSS; Monaco rendering path; font/Unicode handling.
- **Evidence (spike 6, 2026-10-12):** a ~210 KB JS DOM + CSS + layout + software painter runs the real Monaco on QuickJS-ng; element geometry equals Chromium's (every non-SVG box within 0.5 px in 4 scenarios), framebuffers identical on Node and QuickJS. A static replay of the real workbench (the workbench's JS was not run on it) puts 422 of 566 boxes within 1 px and 924/975 `offsetWidth` values right; the CSS surface needed is block/inline/inline-block/absolute/fixed/relative/flex, no grid/float/table. Known gaps: SVG, `box-shadow`, rounded borders, rotation, kerning for Inter, `env(titlebar-area-*)`, Canvas 2D. **Cost:** on QuickJS one cold workbench pass was 7.3 s style+layout and ~3.1 s paint (5.7× and ~11× slower than Node); see spike 7 below for what was native-ised and what the real bottleneck is. Not tested: GDI/Windows, the workbench running on this DOM (events, focus, IME), webviews (table layout), 64-256 MB RAM budgets. Details: [spikes/06-rendering/README.md](spikes/06-rendering/README.md).
- **Evidence (spike 7, 2026-10-12):** layout (port of `layout.js`, 620 lines of C) and the rasterizer (display list, 244 lines of C) run as QuickJS modules and reproduce the JavaScript results exactly (identical geometry; byte-identical framebuffers on 5 pages, x86-64 and x86-32). Workbench replay on QuickJS-ng: layout 0.36 to 0.48 s → 0.02 to 0.03 s, paint 3.1 s → 0.05 s, boundary cost ~15 ms. **The real bottleneck is style resolution:** 1.7 to 1.9 s per full restyle (warm), 90 % of it selector matching (1.34 M candidate tests for 3,783 matches); the JS-only Bloom filter already cuts matching 3×. So the render stack's split is: DOM, cascade (needs a native or at least incremental matcher), layout and paint in C; fonts are still parsed in JS (a native font reader is open); Windows/GDI untested. Details: [spikes/07-native-render/README.md](spikes/07-native-render/README.md).

## D-006 — Process and IPC model — proposed (pending Phase 1)
- **Open:** processes vs threads for UI / extension host / shared process; replace Electron IPC with named pipes or sockets.
- **Evidence so far (spike 2, 2026-10-12):** the extension host talks to its renderer over one `MessagePort` obtained from `process.parentPort`: `Ready` → init JSON → `Initialized` → length-framed RPC. Four Node-side bundles run as separate QuickJS instances in 11 to 33 MB each. A replacement host needs `MessagePort`-style endpoints (or an adapter with `on('message'|'close')`, `start`, `postMessage`). Details: [spikes/02-node-shim/README.md](spikes/02-node-shim/README.md).
- **Evidence (spike 5, 2026-10-12):** child processes use Node's own protocol (`NODE_CHANNEL_FD`, one JSON message per line) over a `socketpair`; spawn, fork, pipes and TCP/unix sockets are as fast as Node's (32 MB through `cat` 57 ms vs 51 ms; 2,000 IPC round trips 172 ms vs 129 ms). The language servers and tsserver need exactly that and nothing else. On Windows the engine's stock event loop waits only on stdin and worker ports, so the process/IPC layer needs a host-owned loop (IOCP on NT; sockets + helper threads on Win9x; unverified). The IPC transport can be inherited anonymous-pipe handles or loopback TCP without changing the protocol. [spikes/05-child-process/README.md](spikes/05-child-process/README.md).

## D-009 — CPU baseline: one Pentium-class x87 binary, integer rasterizer (2026-10-12) — accepted
- **Decision:** The native code (QuickJS host, `layout.c`, `render.c`) is built as one 32-bit x86 binary for Pentium-class x87 CPUs: no SSE/SSE2, no MMX, no CMOV (`-march=i586 -mno-sse -mno-sse2 -mno-mmx -mfpmath=387`, x87 precision set to 53 bits at start-up). Rasterization uses an integer implementation; the double-precision one stays as the byte-exact reference.
- **Why:** Many target machines (Athlon/K7, Pentium III, K6) lack SSE2; requiring it would exclude most of them. Measured in spike 7: the build passes all comparison tests with 0 SSE/MMX/CMOV instructions; the double rasterizer was 6× slower on x87 (~300 ms/frame) but the integer one needs 4 ms on the baseline and is within 2 colour levels of the reference; layout and the JS-side style work are not sensitive to SSE2.
- **Alternatives (not chosen):** require SSE2; ship separate SSE2/x87 builds; runtime CPUID dispatch (worth revisiting only if SIMD kernels are written); soft-float for CPUs without an FPU.
- **Open:** run on a real or emulated old CPU; the Windows C runtime and Oniguruma/wasm3 native builds were not checked for newer instructions; 128 MB RAM budget for the oldest target (owner: back-port after the application works).
