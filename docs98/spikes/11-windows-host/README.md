# Spike 11 — the host on Windows (x86, Windows 7 first)

**Question** ([CHECKPOINT](../../CHECKPOINT.md), D-006, spike 5's "Windows" analysis, spike 10's last open item): the whole stack (QuickJS host, Node shims, process model, main-process shim, software renderer) has only ever run on Linux. What does it take to run it on Windows 7, 32-bit, with a real window and no runtime to install?

- **Almost everything below ran under Wine 9.0 on Linux (cross-compiled with mingw-w64).** Wine is not Windows; it found real bugs (Win32 error codes, module identity) but can hide others. The self-test package (`package/`, `host/package_win.sh`) was then run on a **real Windows 7 Professional, build 7600 (no service pack), x86, 2 GB RAM, 2 vCPUs of an AMD Ryzen 5 5600G VM**: all 5 tests (host start, processes/pipes/IPC/kill, `child_process.fork` through the Node shims, `net` over named pipes, the GDI window) **passed unchanged** (`results/win7-vm/`). The window log shows every event type arriving with the right coordinates and codes: left/middle/right buttons with the button mask (including chords), wheel steps of ±120, key down/char/up with scan codes, Caps Lock toggling the case of the typed characters, Enter. Whether the gradient was drawn correctly was not reported (the log cannot show pixels). The web and desktop workbench have not yet been run there.
- **Target of the build:** Windows 7 SP1 and later, 32-bit (`-march=i586 -mno-sse -mno-sse2 -mno-mmx -mfpmath=387`, the baseline of spike 7) and 64-bit. Imports only `kernel32`, `user32`, `gdi32`, `msvcrt` (all present in a clean Windows 7; no Visual C++ runtime). **Windows XP is blocked by four functions** QuickJS itself imports (below).
- **Host:** QuickJS-ng 0.17.0 + the spike 5/7 native modules; the same JavaScript as on Linux.

## Verdict

1. **The host cross-builds and runs on Windows** (1.6 MB exe). The stock QuickJS compiles for mingw with a small patch of `quickjs-libc.c` (four hunks in the Windows poll loop); the spike 7 rasterizer and layout engine needed one change (a timer, `render.c`) and render **the same pictures**: the web workbench boot of spike 8 runs on the .exe under Wine and reaches the same Welcome / chat screen.
2. **A native process/pipe layer for Windows (`winproc.c`, ~600 lines of C) replaces POSIX `proc.c` behind the same JavaScript.** Overlapped named pipes, `CreateProcess` with handles passed by value, waitable process handles, named-pipe servers: `child_process.fork()` with an IPC channel (the spike 5 tests: JSON messages up to 280 KB, stdio pipes, disconnect, kill, spawn failure), `net` over `\\.\pipe\...`, `spawnSync`, 2.5 MB through a pipe — all pass (`results/`). This is the part of spike 5's "Windows event loop" analysis that was open; it is solved without changing QuickJS beyond the event-loop hook.
3. **A Win32 window (`winwin.c`, ~145 lines, GDI only).** The framebuffer of the native rasterizer is blitted with `BitBlt`; mouse (with capture and hover tracking), wheel, keyboard (virtual keys, `WM_CHAR` text) and size events reach JavaScript from inside the QuickJS event loop (the loop waits with `MsgWaitForMultipleObjects`). `window_host98.mjs` turns them into DOM events (hit testing with `elementFromPoint`, focus, `keydown`/`input` for Monaco's input area).
4. **The desktop workbench of spike 10 runs on the Windows .exe under Wine in a window**: main process (VS Code's own electron-main bundle, Windows code paths: `isWindows` branches in `mainImpl.js`), shared process, file watcher, extension host, agent host (crashes, as on Linux), renderer; F1 typed on the X keyboard through Wine opens the real Command Palette (`results/desktop-window-wine.png`). The headless run settles in 76 s under Wine (Linux native: 60 s for spike 10's folder run); a real Windows number is not known.
5. **What it still needs is host work and a real machine:** TCP sockets (Winsock), `.cmd`/`.bat` spawning, the XP condition-variable gap, Windows 9x (no `W` APIs, no overlapped pipes), native addon stand-ins, and every number on real hardware. See "Gaps".

## How to run it on a VM

1. Windows 7 SP1 32-bit, 2 GB RAM, 2 vCPUs, 1280×800, no 3D (the spec given in the conversation).
2. Unzip `dist/vscode98-win-selftest-x86.zip` (built by `host/package_win.sh dist-dir x86`; not committed, it is a build product) anywhere and run `selftest.cmd` in `cmd.exe`. It writes `results\` (system info, one text file per test). The window test needs you to move the mouse over the window, click, scroll and type for 15 s.
3. Send `results\` back. The desktop workbench is a second package (`host/package_desktop.sh`, 42 MB zipped, 166 MB unpacked: the app bundle without source maps, the 60 `node_modules` packages the app loads with their native binaries emptied, `theme-defaults` and the git extension's compiled output): unzip, run `run-desktop.cmd [width height]` (default 1000×700; the VM's screen is 1024×768) and send `results\desktop.txt`. Under Wine the package boots to the Explorer with the sample folder in a window (802 elements after 42 s, still filling).

**First real-Windows desktop run (Windows 7, build 7600): the window stayed blank** (8 elements, 0 layouts, `TypeError: cannot read property '__nid' of null` in the native font registry). Cause: the renderer's font table names Linux paths (`/usr/share/fonts/...`) and `loadFile` returned null for all of them; under Wine those paths resolve to the Linux host's real font files, so the bug was invisible there. Fix: `globalThis.__fontRoot` relocates the table (`--font-dir`, default `<package>/fonts`), the package ships DejaVu, Liberation and Inter (18 MB, licences in `fonts/LICENSES`), and the Wine run was repeated with `/usr/share/fonts` renamed away: the workbench renders completely from the bundled fonts. Two smaller findings from the same log: `@github/copilot-sdk` is missing in the package (agent host, expected: it crashed on Linux already, now it fails at resolution), and `mkdir` of an existing directory reported EEXIST once on Windows (a raw Win32 code; now re-stat after a failed `mkdir`).

## Gaps and findings

| | |
|---|---|
| **Only partly verified on Windows** | the process, pipe, fork, named-pipe and window-event tests pass on a real Windows 7 (build 7600, x86, 1024×768 screen); the picture drawn in the window, the web/desktop workbench and all timings were only run on Wine so far. The VM's screen is 1024×768: the 1280×800 default window of the desktop harness does not fit, use `--width 1000 --height 700`. Known differences that matter: Wine's named pipes, overlapped I/O and `MsgWaitForMultipleObjects` are re-implementations; GDI under Xvfb has no DWM/Aero; process creation timing; DPI virtualization (the exe calls `SetProcessDPIAware` when present) |
| **Windows XP does not load the exe** | QuickJS imports `InitOnceExecuteOnce`, `InitializeConditionVariable`, `SleepConditionVariableCS`, `WakeConditionVariable` (Vista+, for worker threads / `Atomics.wait`). Everything of mine avoids Vista-only calls (`check_imports.sh`). Fix: replace the four with `GetProcAddress` fallbacks built on events and a critical section (a small patch of `quickjs.c`/`quickjs-libc.c`'s pthread-like layer) |
| **Windows 9x** | not started: no `W` entry points (all of `winproc.c`/`winwin.c` use them) and no overlapped I/O on pipes (NT only). The thread-based reader for non-overlapped handles already exists (it is what handles inherited std handles), so pipes can be done with threads; `CreateProcess` + handle inheritance exist on 95/98 |
| **TCP / `dgram` / `tls`** | `listen`/`connect` by host and port return ENOSYS (needs Winsock with `WSAEventSelect` handles in the same wait set). Named pipes (what VS Code uses on Windows for its own IPC) work |
| **Pipe half-close** | a pipe has none: `socket.end()` sends the queued data, then closes the whole handle; a peer that keeps sending after our `end()` is lost |
| **`.cmd` / `.bat`** | `spawn` without a shell cannot start them (as in Node ≥ 20.12); `shell: true` goes through `cmd.exe` |
| **Symlinks, `lstat`** | QuickJS has none on Windows; `lstat` is `stat` |
| **Wait set limit** | 64 handles (`MAXIMUM_WAIT_OBJECTS`): fine for a workbench (a dozen pipes), a concern for many sockets |
| **Native addons** | still the spike 10 stand-ins (JSON storage instead of SQLite, polling watcher) plus new ones for the Windows-only packages; `@vscode/spdlog` stub means no log files |
| **Agent host** | crashes at start-up as on Linux (out of scope on old Windows, D-008) |
| **Speed** | Wine: 76 s to settle (Linux native 60 s with a folder, 28 s without). Real hardware unknown |
| **Startup of the window** | the first paint happens after the workbench's own start-up; a window with a splash would show something earlier |

**Bug found by the VM's status lines:** the idle workbench was repainted about 12 times a second (paints 50 → 2428 over 200 s with no layout pass), and the renderer's working set swung between 513 and 652 MB. `present()` makes Windows send `WM_PAINT`, the window forwarded it as a `paint` event and the DOM driver repainted on every event, including that one. Fixed (no repaint on `paint`/`focus`/`leave`) and the 4 MB backend buffer is reused (`NativeBackend.reset()`); after the fix an idle workbench paints 0 times (5 paints in 138 s under Wine, flat memory).

### Interaction on the VM, round 1 (desktop package v4): clicks work, the editor does not, file open takes 30 s

The VM report: files in the Explorer can be clicked, the editor shows the I-beam cursor, but typing, clicking into the text and selecting do nothing, and the text of an opened file shows up about 30 s after the click. Reproduced and fixed with a headless scenario (`10-main-shim/host/scenario_click.mjs`: open a file, then press at real coordinates with the same pointer + mouse events the window host sends) and with `xdotool` against the real window under Wine (`--debug-input 1` logs every window event, the element under the pointer and `document.activeElement` before/after each press).

Root causes, in the order they were found:

1. **The file text appeared late because the window was painted only when `doc.__dirty` was set.** Code that reads geometry (Monaco measures all the time) runs a layout pass itself and clears the flag, so most changes were never painted until something else dirtied the document. The tick now paints whenever a layout pass has run since the last paint (`doc.__passStats.length`).
2. **Clicks into the editor text were ignored because our DOM had no `ELEMENT_NODE`/`TEXT_NODE` on instances.** Monaco writes `child.nodeType === child.ELEMENT_NODE`; browsers define the node-type constants on `Node.prototype`, our `Node` only had them as statics. `PartFingerprints.collect()` therefore returned an empty path for every target, the mouse hit test fell through to "unknown" (inside a `try/catch` that swallows everything), nothing focused Monaco's hidden `textarea`, and the window host's own default action (blur the active element, since nothing focusable was under the pointer) left `activeElement` at `body`. Keys went to `body`. `dom.js` now defines the constants on the prototype.
3. **`document.caretRangeFromPoint` returned `null`.** The hit test of the text itself (`_doHitTestWithCaretRangeFromPoint`) needs the character offset under the pointer. Implemented in `env.js` on the layout's text fragments (nearest fragment on the line containing `y`, nearest character boundary in `x`).
4. Pointer events: Monaco's editors listen to `pointerdown`/`pointermove`/`pointerup` (drag selection) as well as `mousedown`; the window host now sends the pointer event first, then the compatibility mouse event (skipped, as in browsers, when `pointerdown` was cancelled), and focuses the clicked control only if the press was not cancelled (Monaco cancels it and focuses its own input area).

Result under Wine + Xvfb + xdotool on the real window: click `hello.txt`, click into the text, type `abc` → `helloabc vscode98`, caret drawn, tab shows the modified dot.

**File open time** (scenario `scenario_edit`, Linux, QuickJS-ng, 55 to 98 layout passes): 12.5 s → 6.6 s. Two changes: the per-rule part of the rule index (parsed selectors, expanded declarations, Bloom-filter bits) is cached per `CSSStyleRule` so the index rebuilds that follow every `<style>` change (24 to 40 during boot, 14 to 16 k rules each) only allocate the entries again; and `analyzeIndex` is incremental (it scans only the selectors it has not seen; its result only ever grows, and it starts over when most of what it remembers is gone). Both keep the spike 9 fuzzer at 0 mismatches (7,500 passes). What is left of the 6.6 s: style 4.2 s (rule index 1.0 s, planning 0.5 s, **matching 1,400 restyled elements about 1.6 ms each**, computed styles 1.0 s) and layout 1.4 s. The first click restyles 481 elements at once (a class on a high container changes). One walk over the candidate lists now serves an element and its two pseudo-elements (`matchedDeclarationsAll`). Next, if it is still too slow on the VM: bucket the 282 universal-bucket rules (168 are `:is(...)`) by the keys of their arguments, which are 56 % of the 5 M candidates tested per boot (97.6 % of the tests that pass the Bloom filter fail), and a native matcher.

**Confirmed on the VM with package v5** (`results` of the user's run): typing lands (`helloabc`/`testing 3`), the editor takes focus on a click (`active-after=textarea.inputarea`), double-click and drags are handled, no listener errors. The opened file's text appeared within about 20 s of the click (v4: 30 s).

### Interaction and boot speed, round 2 (package v6)

The VM report: boot is slow, a click into the editor takes a few seconds to react, typing is slow. A profile of the settled workbench on the sandbox (`10-main-shim/host/scenario_keys.mjs`: busy time of a click and of every key split into event handling, frame callbacks, style, layout, paint, the way the window host drives the document; `scenario_match.mjs`: selector matching on the settled DOM against the plain matcher as oracle) showed:

- **Selector matching dominated restyling** (0.78 ms per element; 5 M candidate rules considered per boot, 97 % failing at the subject compound). 168 universal-bucket rules were `:is(...)` compounds, 578 rules sat in the `.codicon` bucket. Fixes in `css.js`/`selectors.js`: rules whose subject is `:is()`/`:where()`/`:root` are filed under the keys of their alternatives; multi-class compounds under the rarest class; "one of" ancestor Bloom groups for `:is()` compounds in the ancestor part (131 k of 147 k failing descendant climbs had one); a per-pass memo of "does this element or an ancestor match this compound". Matching per element 0.78 → 0.31 ms (microbenchmark, 0 mismatches against the plain matcher).
- **Rule index** (every `<style>` change used to rebuild 12 to 16 k entries and diff them by signature: 10.4 s of the 54 s boot): `diffIndex` now compares by rule identity, the index is extended in place when only the tail of the rule list changed (entries are the last of their buckets, so they can be popped), `analyzeIndex` only scans new entries. 10.4 s → 3.6 s.
- **Planning** spent 10 ms per pass in `shapesMatch` (hundreds of shapes from `:first-child`-style rules, each tried against every inserted element): shape lists are now indexed by id/class/tag.
- **The big one: AI features.** The chat panel, welcome dialog, agent status bar and secondary side bar were half of the boot's layout passes (322 → 66), elements (1,011 → about 500) and style+layout time (25 s → 8 s). The AI features are out of scope for old-Windows builds (D-008); the harness now seeds `chat.disableAIFeatures`, a hidden secondary side bar, no command center, no layout controls, no breadcrumbs/minimap/tips/experiments into a fresh user `settings.json` (only when none exists). The result is the classic VS Code window (menu bar in the title bar, Explorer, editor, status bar).

Sandbox numbers (Linux x86-64 QuickJS, the same code as the Windows host): workbench ready (UI and settled) 36 s → about 19 s; click into the editor 0.9 s → 0.5 s of work, steady-state key 55 ms → about 50 ms including paint at half the element count; file open 12.5 s → 3.5 s. Compiler flags are not the lever: SSE2, i686 and `-O3` builds ran within noise of the i586 build (Wine: boot 60 to 69 s, matcher 340 to 378 ms).

**The VM is much slower than the sandbox.** The workbench reaches about 800 UI elements after about 12 s natively, about 40 s under Wine here and about 127 s on the VM (VirtualBox, 2 GB, 2 vCPUs of a Ryzen 5 5600G, 128 MB video, VT-x, Hyper-V paravirtualization). `bench.js` / `run-bench.cmd` (ten micro-benchmarks, about 9 s here, 16 s under Wine) are in the package to tell whether that is general VM slowness or something specific.

**Round 2 on the VM (package v6, the user's numbers): the VM is not slow.** `bench.js` total 7.2 s on the VM against 9.1 s native Linux and 16.5 s under Wine on the sandbox (the Ryzen is simply fast), yet the workbench took 51 s to open (about 19 s native) with the first 45 s a blocked event loop (`[status] t=45s elements=14`; the first status line should have come at 15 s). File open 1 s, typing fine after an initial delay, **Enter did nothing**.

Two Windows-only costs found by reading the log against the benchmark, neither visible on Linux:

1. **`js_load_file` is quadratic where `realloc` moves large blocks.** QuickJS reads a file in 8 KB pieces and reallocates `len + n + 1` after each piece; a 15 MB bundle is 1,900 reallocations, free on glibc (`mremap`) but a full copy each on the Windows heap: 15 MB `std.loadFile` took **1,775 ms under Wine against 22 ms on Linux** (37 ms after the fix), more on a real heap. Every module, CSS, JSON and NLS file goes through it. `patch_libc.py` now replaces it with a read of known size (one allocation; geometric growth for pipes).
2. **Timer resolution.** QuickJS clamps `setTimeout(0)` to 1 ms and the Windows poll waits with `WaitForMultipleObjects`/`Sleep`, which wake on the 15.6 ms system tick: 1,000 chained zero timers (a few thousand happen during a workbench boot: `setImmediate` of the Node shims, `timeout(0)`, `RunOnceScheduler`) cost 15 s instead of 1. `spike_init` now calls `timeBeginPeriod(1)` (`QJS98_TIMER_RES=0` turns it off for comparison). `bench2.js` (`run-bench2.cmd`) measures timers, stat, big-file read and compile; run it with and without `set QJS98_TIMER_RES=0`.

Under Wine, the first `[status]` line (window opened, UI built) went from t=40 s to t=10 s with the file-read fix alone.

**Enter:** `char` events below 32 were dropped as "control keys handled through keydown", but Enter is text in a `<textarea>` (Monaco's input area gets the line break from the browser): it now inserts `\n` with `inputType: 'insertLineBreak'` (a single-line `<input>` only gets the key events), and a character is not generated when the `keydown` was cancelled (as in browsers).

**Round 3 (package v7 on the VM, the user's report):** workbench opens in 10 s (51 s with v6), a file opens in 1 s, a click into the text is almost instant, typing is smooth, Enter works; still laggy: selecting text by dragging, F1 takes 1 to 2 s. `bench2.txt`: file read 15 ms, 3000 stats 56 ms, 1000 chained `setTimeout(0)` 1.95 s with the 1 ms timer resolution (the clamp, not a 15 ms tick), compile 12 MB 1.0 s. The VM's first `[status]` line at t=15 s shows 445 elements; the first style pass (rule index 3.2 s: CSS parse, selector parse) was the biggest piece of the remaining boot.

Round 3 changes (package v8; sandbox numbers, Linux QuickJS):
- **Drag selection** was ~70 ms per mouse move (Monaco 17, style 10, layout 17, paint 20). `render.c`: opacity layers were allocated with `calloc` at the size of the whole clip (2.8 MB, 2.5 ms each, four per frame) and composited pixel by pixel; layer buffers are now pooled (kept all zero) and the integer rasterizer records the bounding box of what it drew on a layer, composites only there and clears only there afterwards. Raster per drag frame 13 to 24 ms → 3 to 4 ms, frame checksums identical before and after. `layout_pack.js`: the packed style record of a box is cached per computed-style object (a `__packVerify` mode recomputes and compares: 17,241 checks, 0 differences); layout per pass 11 → 7 ms (key) and 17 → 9 ms (drag move).
- **Parsers**: selector parsing 1,179 → 312 ms for the workbench's 14 k selectors (an identifier is one sticky-regex match, whitespace is a char-code loop), CSS parsing 795 → 400 ms for 2 MB (char codes instead of one-character strings, `splitDecls` slices instead of appending). Differential tests against the previous parsers: identical ASTs for 11,172 selectors and edge cases, identical rule trees (3.2 MB of JSON) for the whole stylesheet plus nasty inputs.
- Boot (sandbox, no AI): UI and settled in 13 s (19 s before this round).
- F1: 21 layout passes of 20 to 50 ms plus a 1,460-mutation pass (484 inserted nodes); not changed beyond the general speedups. Next candidates: skipping layout when only paint properties changed (15 of the 21 passes), dirty-rectangle painting, an incremental box tree.

**Round 4 (package v8 on the VM, the user's report):** launch 16 s status line with 1,038 elements after typing/F1 (total until stable 22 s); dragging to select improved but still noticeably slow, F1 still 1 to 2 s. Changes for package v9 (sandbox numbers):
- **Hit testing**: `elementFromPoint`/`elementsFromPoint` computed a `DOMRect` through four temporary arrays for every element of the tree (5.8 ms per call, two calls per mouse move). `__rect` has a fast path for boxes without transform or scrolled ancestor (same numbers), and `elementFromPoint` stops at the first hit: 1.5 ms per call; the event part of a drag step 16 → 8 ms.
- **Style-only passes keep the previous layout.** A pass whose log only holds attribute/class/style/state changes (no inserted or removed nodes, no text, no layout attributes), at the same viewport, and whose restyled elements differ from before only in paint-only properties (`PAINT_ONLY` in `layout.js`: colours, backgrounds, shadows, outlines, radii, opacity, cursor, z-index, ...) gets no layout: the restyled elements' boxes (and their text boxes, text fragments and anonymous boxes) are given the new style objects. `doc.__verifyStyleOnly` lays everything out again after each such pass and compares every box's geometry and style reference: 26,473 boxes over boot, file open, click, typing, drag, F1 and Escape (three times each), 0 mismatches. 59 of 221 passes in that run were style-only; the others had inserted/removed nodes (95), a layout-relevant style change (54), or a `type` attribute (10).
- Drag step on the sandbox: 70 ms (v7) → 36 ms (event 8, style 10, layout 9 to 15, paint 9).

**Round 5 (package v9 on the VM):** dragging much better, F1 0.5 to 1 s ("works well enough"), typing/selecting/Enter fine. Two bugs, neither a missing feature:
- **Ctrl+Z / Ctrl+Y (and every Ctrl+letter shortcut) dead on Windows only.** VS Code's Windows keyboard dispatch builds a `WindowsKeyboardMapper` from `native-keymap.getKeyMap()`; our stub returned an empty map, so letters had no key code. `10-main-shim/host/stubs/native-keymap.mjs` now returns a US layout on win32 (generated from the table in `src/vs/workbench/services/keybinding/test/node/win_en_us.js`). Ctrl+Z, Ctrl+Y, Ctrl+Shift+P verified under Wine (`--debug-input 1` logs `[input] key ...`). Layouts other than US are not queried yet.
- **Menu bar dropdowns misplaced, clipped, covered and unclickable.** Four causes: (1) the menu is positioned with `titleBoundingRect * getDomNodeZoomLevel()`, and our computed style had no `zoom` (empty string, factor 0, so the menu sat at 0,0): `zoom` now computes to `1`; (2) a `position:fixed` box inherited its ancestors' overflow clips (the menu bar button clips to its own 20 px): the painter resets the clip for fixed boxes (`OP_RESET_CLIP` in the native display list, `render.c`); (3) the dropdown (fixed, z-index 2000) was painted in the title bar's paint order, so the banner, side bar and editor covered it: fixed boxes with a positive z-index are now collected and painted last, sorted by z-index (`Painter.paintTopLayer`); (4) `elementFromPoint` ignored that order, so hover and clicks went to the editor under the menu: hit testing tries the same top-layer boxes first (`Document.__topLayerBoxes`, cached per layout pass). Verified under Wine: File and Edit open and switch on hover, the item under the pointer highlights, Edit > Undo undoes. Still approximate: a top-layer box inside an element with `opacity < 1` is drawn unfaded, and stacking contexts other than the root are not modelled.

Also found: the window host opens after the script import but the whole workbench build is one long synchronous stretch, so the first `[status]` line (and the 60 s screenshot) arrives late; `--progress <s>` logs a timeline in any mode.

### Round 6: feature audit instead of XP (packages v11/v12)

Direction from the owner after v10: XP is a back-port, so every feature has to work first. v10 only had the basics (typing in the editor, menus, F1); search, New File, New Folder and every text box outside the editor did not work. Round 6 is a systematic audit: each feature is driven through the **same input driver as the window** (`06-rendering/host/dom/input_driver.js`, also used by the headless scenarios in `10-main-shim/host/scenario_*.mjs`) and the result is read from the DOM, so a feature that works in a scenario works in the window. Scenarios are kept as regression tests (see [FEATURES.md](../../FEATURES.md) for the status table).

What was missing or broken, and the fixes:

- **Text controls** (`06-rendering/host/dom/textmodel.js`, `textcontrol.js`): `<input>`/`<textarea>` had no editing model. Now: `value`, selection (`selectionStart/End/Direction`, `setSelectionRange`, `select`, `setRangeText`), `maxLength`, `readOnly`, undo/redo history, `beforeinput`/`input`/`change` events (change only after a user edit, on blur/Enter; a script's `value=` never fires one), caret, selection and `::placeholder` painting, mouse selection (drag, double click word, triple click line), keyboard (arrows, Home/End, Ctrl+arrows, Shift selection, Delete/Backspace, Ctrl+A/C/X/V/Z/Y), clipboard events with a `DataTransfer` that has `items`, `document.execCommand`. The clipboard is the Windows clipboard (`winwin.c` `clipboardGet/Set`, CRLF to LF), with a memory fallback.
- **One input path** (`input_driver.js`): focus, Tab navigation, button and checkbox activation, hover/active state with `mouseenter/leave` and `pointerenter/leave`, triple-click counting, wheel, text input; the window host and the scenarios both use it.
- **Stacking contexts** (`stacking.js`): paint order and hit test now follow CSS appendix E (z-index on flex/grid items counts, fixed boxes ignore ancestor clips, overflow-aware hit test that stops at fixed ancestors). Fixes dropdowns hidden under modals and menu items that could not be clicked.
- **`<select>`** (`selectmodel.js`): `options`, `selectedIndex`, `value`; the settings tree probes it to size its rows (before, rows overlapped or were blank).
- **DOMPurify**: needs `document.implementation`, `NodeIterator`/`TreeWalker`, `DOMParser` with a separate document and `Node.prototype` accessors. Before this, Markdown (settings descriptions, hovers, extension details) was shown as raw HTML.
- **Wheel scrolling**: Monaco reads the legacy `wheelDeltaY` first; `WheelEvent` now sets `wheelDelta*` (= -delta × 1.2).
- **Editor context menu**: the editor renders its context menu inside a Shadow DOM when `editor.useShadowDOM` is true (the default), and our DOM has no `attachShadow` (it throws). The harness seeds `editor.useShadowDOM: false`. Shadow DOM itself is still missing (webviews and some widgets may need it).
- **Search**: ripgrep 13.0.0 i686 (`host/fetch_rg.sh`, sha256 checked, goes to `node_modules/@vscode/ripgrep/bin/rg.exe`); it imports SRW locks (Win7 has them), newer builds need `WaitOnAddress`/`ProcessPrng` (Win8+).
- **File dialogs and trash**: `window.dialogStyle: custom` and `files.simpleDialog.enable` (no native dialogs), `shell.trashItem` through `SHFileOperationW` (recycle bin).
- **Terminal**: `node-pty` stand-in over pipes (`stubs/node-pty.mjs`), xterm.js modules in the package, `<script>` injection support (dynamic scripts execute and fire `load`), the pty host started ahead of time (its startup exceeded the workbench's 5 s timeout), `cmd.exe` as the default profile. Windows 7 has no ConPTY: there is no real console, the line discipline (echo, line editing) is local in the stand-in.
- **Pointer capture** (`setPointerCapture`): pointermove/up go to the capturing element (scrollbar sliders, sashes); `MouseEvent.offsetX/offsetY` are relative to the target (Monaco's scrollbar track click used them: it always jumped to the top).
- **Page text selection** (`docselect.js`, `Range`/`Selection` in `dom.js`): real ranges with tree-order comparison and `toString`, `user-select` aware mouse selection (caret, drag, double click word, triple click block, shift+click), painted as a highlight behind the glyphs, Ctrl+C copies it (a `copy` event first).
- **Drag and drop** (`dnd.js`): a press on a `draggable="true"` element and 4 px of movement is `dragstart`, then `dragenter/dragover/dragleave` on the element under the pointer, `drop` when the last `dragover` was canceled, `dragend`. Tab reordering and moving files in the Explorer (with its confirm dialog) work.
- **Window resize and page zoom**: `env.resize(w, h)` (it did not exist: a resized or maximized window kept the boot size) updates `innerWidth/Height`, restyles (viewport units, media queries) and fires `resize`; zoom lays the page out in `window / factor` CSS pixels and paints through a `ScaledBackend` (`zoom.js`), mouse coordinates are divided by the factor. Ctrl +/- / Ctrl 0 work through the real `webFrame.setZoomLevel` path.
- **Search backend**: the bundles import `@vscode/ripgrep-universal` (not `@vscode/ripgrep`); the package carries `bin/win32-ia32/rg.exe` (13.0.0) there (`Cannot find module '@vscode/ripgrep-universal'` on the first Wine run of the new package).

Verified on Linux with `scenario_lang`/`tour`/`misc`.
- Stale state in test profiles caused false failures (dirty tabs restored from Backups, orphaned `qjs-spike7` processes, `code.lock`); `runsc.sh` now cleans them before each run.

### Round 9: "unusable" report on v12 (package v13)

Owner's report (VM, 2 vCPU / 2 GB): over a minute to open, 5 s for a context menu, over a minute for a new file/folder to show up, slow menus. Findings, measured with the new `10-main-shim/host/scenario_lat.mjs` (wall-clock latency of the explorer context menu, menu bar and New File, idle and while the language servers start; `taskset -c 0-1` stands in for 2 vCPUs):

- **`code-icon.svg` took 9.3 s to decode on the sandbox** (about 70 s on the VM). The SVG rasterizer rendered the 1024-unit viewBox at 2x = 2048 x 2048 (a 64 MB float buffer, 16 M pixels, in JS). It is first needed when the first menu opens. The raster is now capped at 256 px on the longest side (it is scaled to the box when drawn): 130 ms. The first context menu went from 10.5 s to 1.1 s.
- **v12 shipped all 86 built-in extensions; v11 shipped `theme-defaults` and `git`.** The extension host plus two `tsserver`s (opened by the first `.js` file, for example a new `test.js`) made 10 processes and 1.1 GB against 5 processes and 600 to 770 MB in every earlier log, on a machine with 2 GB. `spawn` has a `priority: 'low'` option now (`proc.c`: `nice(10)`; `winproc.c`: `BELOW_NORMAL_PRIORITY_CLASS`, which children inherit); the extension host and everything it starts run at low priority so the UI (renderer) gets the CPU first. With the servers starting, the menu latency stays at the idle level instead of 1.5 to 3 times it (Linux, 2 CPUs).
- **Stacking bug found on the way**: positive and negative z-index contexts were kept in tree order instead of z-index order (`stacking.js`), so a popup (z-index 2575) could be painted and hit-tested under the Settings modal when its element happened to come earlier in the DOM. Fixed (the Settings drop-down scenario started to fail once the timing of the boot changed).
- Style matching: 259 candidate rules are examined per element (110 from the universal bucket); cheaper rejection (first Bloom word precomputed, dedupe token only for entries filed in several buckets) made rule matching 16 % faster. Style recomputation is still about 0.8 ms per element (0.45 ms matching, 0.25 ms computing, 0.15 ms the rest): a menu opening costs about 0.6 s on the sandbox with 2 CPUs, so about 5 s on the VM is the remaining floor of this engine. Sharing styles between siblings would help only 12 % of elements (measured), so it was not built.
- Not changed: boot time (about 32 s on the sandbox with 2 CPUs; the 8 x slower VM takes over a minute).

### Round 10: first real Windows 7 laptop (package v14)

The owner moved from the VM to a real Windows 7 laptop (bench 19.3 s, about 2.7 x slower than the earlier VM on the desktop). Report on v13: about 25 s to load, about 1 s from a click to the caret moving, 2 to 3 s to switch files, 1 to 2 s for a menu, 15 to 20 s for a new file or folder to show up (the second one only after clicking around), a click between letters put the caret at the end of the line, Reveal in File Explorer did nothing.

- **Messages waited for the next write (the stalls).** `winproc.c`'s overlapped pipe write queues what is written while a write is in flight, and the queue is sent when that write completes; but the completion was only waited for when JavaScript had set a write handler, which the IPC writer never does when the write is accepted. So a message written right after another one stayed in the queue until the next write on the same pipe, in either direction (renderer <-> main, main <-> utility processes). Found by tracing request ids at both ends (`--debug-ipc`, `VSCODE98_TRACE_IPC`, `UTIL_TRACE`, `VSCODE98_TRACE_PIPE`, probes in the bundles): `localFilesystem.stat` for the new file was processed by main only when the next renderer request arrived, and its answer reached the renderer only with the next message from main. Fixed in `win_collect` (an in-flight write is always waited on). Under Wine: a new file is on disk 330 ms after Enter and appears in the explorer and the editor, a new folder 440 ms; before, it never completed without further input. This also delayed every other exchange (file reads when switching files, extension host requests), so it is likely part of the general sluggishness too.
- **Caret at the end of the line** (`env.js` `caretRangeFromPoint`): the scroll compensation used the layout position of the element under the point, and an inline box (the token span of an editor line) has none (0, 0), so x was shifted by the line's whole left offset. It now uses the nearest block box. Scenario `scenario_misc --only caret`.
- **Reveal in File Explorer / open path / open link**: `shell.showItemInFolder` (`explorer.exe /select,"..."`), `openPath` and `openExternal` (`rundll32 url.dll,FileProtocolHandler`) in the electron stub; `app.getJumpListSettings` stub (main logged a TypeError at startup).
- **Unhandled rejections** in Node-like processes are reported only when still unhandled a macrotask later (`proc_setup.mjs`); QuickJS reports a rejection the moment it happens, before an `await` one microtask on attaches the handler, which printed thousands of handled ENOENT stats to stderr. IPC readers no longer stop at a message handler that throws.
- **Event loop**: more than 63 waitable handles are served in turns with a capped wait (`win_collect`/`win_max_timeout`), instead of silently ignoring the rest.
- **Wine/Xvfb in the sandbox**: after a crash of the X server Wine's `CreateWindow` fails with 1400 until Xvfb is restarted (`/tmp/claude-0/wrun.sh` restarts it and stops wineserver gracefully each run).
